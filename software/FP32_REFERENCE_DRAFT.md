## 1. 我们实际要算什么

首版第一线性层：`X[99,64] × W[64,256] + b[256] → Y[99,256]`。下标 `t` 表示 99 个输入位置之一，`j` 表示 256 个输出通道之一：

```text
acc = +0.0f
for k = 0, 1, …, 63:
    product = round_fp32(X[t,k] × W[k,j])
    acc     = round_fp32(acc + product)
Y[t,j] = round_fp32(acc + b[j])
```

`round_fp32` 表示每一步都把精确值舍入成 32 位浮点数。在这个草案里采用“离谁近取谁，恰好居中则取末位为偶数”的规则。乘法和加法**分别**舍入，不做融合乘加（FMA）；`k` 从小到大；偏置在全部 64 项之后**只加一次**。如果硬件分成两个 `K=32` 块，第二块要接着第一个块留下的部分和计算；块边界不是重新置零或再加一次偏置的理由。这些是目前建议的算术约定，硬件尚未确认。

代码在 [`fp32_reference.py`](fp32_reference.py) 中。输入和输出都直接用 32 位浮点的**位模式**表示，如 `0x3f800000` 表示 `1.0f`。运算时，它把每个有限浮点数精确拆成“带符号整数 × 2 的整数次幂”，用 Python 整数完成乘加，再逐次舍入，所以不会暗中采用机器的 FMA 或矩阵库自己的求和树。它不是语音识别精度评估，也不是目前 RTL 已支持的证据。

## 2. 两行两列的小例子，逐个数手算

这个矩阵沿用我们已有定点交接小例子的**实数**，方便硬件同学比较两种格式。它只是合成的线路联调数据。

```text
X = [ 1.0  -2.0 ]       W = [ 2.0  -1.0 ]       b = [ 0.25  -0.5 ]
    [ 0.5   3.0 ]           [ 1.5   0.5 ]
```

按行、按列做四个点积，偏置 `b[j]` 对同一列的每一行都使用一次：

| 输出 | 第 0 项 | 加第 1 项后的部分和 | 最后加一次偏置 | 二进制 32 位 |
|---|---:|---:|---:|---|
| `Y[0,0]` | `1×2=2` | `2+(-2×1.5)=-1` | `-1+0.25=-0.75` | `0xbf400000` |
| `Y[0,1]` | `1×(-1)=-1` | `-1+(-2×0.5)=-2` | `-2-0.5=-2.5` | `0xc0200000` |
| `Y[1,0]` | `0.5×2=1` | `1+(3×1.5)=5.5` | `5.5+0.25=5.75` | `0x40b80000` |
| `Y[1,1]` | `0.5×(-1)=-0.5` | `-0.5+(3×0.5)=1` | `1-0.5=0.5` | `0x3f000000` |

这些数都能被二进制浮点数精确表示，因此适合先检查正负号、行列顺序、偏置通路。测试代码把上面四个十六进制值独立写定，然后运行参考函数逐位比较。

一个 FP32 数的 32 位分为 `1 位符号 | 8 位指数 | 23 位尾数字段`。例如 `-0.75 = -1.5×2^-1`：符号位为 1；实际指数为 -1，存储时加上偏移 127 得到 126；`1.5` 写成二进制是 `1.1`，开头的 `1` 对正规数隐含，尾数字段记录后面的 `.1`。这些字段拼在一起是 `0xbf400000`。这**不是**把实数 `-0.75` 简单乘一个固定倍数后存成整数；所以它与原来 Q8 定点例子的字节完全不同，虽然手算实数答案相同。

## 3. 为什么不能直接用 `X @ W + b` 当 RTL 的逐位答案

线性代数只规定了数学结果；硬件还要决定**每一步怎么算、何时舍入**。例如两个项按 `(a+b)+c` 还是 `a+(b+c)` 求和，FP32 位结果可能不同，因为中间小量会在舍入时丢失。矩阵库也可能重新排列求和、使用融合乘加或采用更宽的内部精度。它们的输出可以用于模型精度研究，却不能在没有约定运算次序前当作逐位 RTL 标准。

一个专门区分 FMA 的小算例：

```text
X = [ -1, 1+2^-23 ]
W = [  1, 1-2^-23 ]
b = 0
```

按本草案，`k=0` 后 `acc=-1`；`k=1` 的**精确乘积**是 `1-2^-46`，先舍入为 FP32 的 `1`，再与 `-1` 相加，得到 `+0`，位模式 `0x00000000`。如果第二项采用一次融合乘加，它保留乘积尾部，得到 `-2^-46`，位模式 `0xa8800000`。因此同样写成“乘加”，中间舍入边界不同，最后的位就不同。

还要检查跨越 **K=32 分块边界**时不丢部分和。做一个只有一行、一列、`K=64` 的小例子：令 64 个 `X[k]` 全为 `+1`；64 个 `W[k]` 除 `W[31]=+2`、`W[32]=-3` 外全为 0；偏置 `b=+0.25`。`k=31`（第一个 32 项块最后一项）后部分和是 `+2`，位模式 `0x40000000`；`k=32`（第二块第一项）后应沿用旧值算成 `+2-3=-1`，位模式 `0xbf800000`；到 `k=63` 仍是 `-1`，**这时才加一次偏置**，得到 `-0.75`，位模式 `0xbf400000`。若第二块重置累计值，会只剩 `-3`；若每块都加偏置，结果会变成 `-0.5`。测试脚本逐点固定了边界两侧和最后结果；生成的 `tile_x/tile_w/tile_bias/tile_expected` 文件可直接用于 RTL 的跨块仿真。

## 4. 三块 16 位 × 1024 存储器与 FP32 的关系

硬件同学确认一块缓存容量为 `1024×16 bit = 2048 byte`。一个 FP32 数占 32 bit，若存到这种缓存中就要**两个**16 位字，因此一块缓存最多放 512 个 FP32 元素。16 位是存储接口宽度，不表示运算自动变成 INT16。

样例暂用以下**候选打包方式**，便于做字级读回测试，**不是已冻结的外存布局**：矩阵按行排列；每个 FP32 位模式先放低 16 位字，再放高 16 位字；生成 `.bin` 时每个 16 位字先写低字节。比如 `-0.75f` 的位模式 `0xbf400000` 拆成 `.mem` 两行 `0000`、`bf40`，对应 `.bin` 四字节 `00 00 40 bf`。`software/examples/fp32_hand_image/` 已生成基础 `x/w/bias/expected`、舍入边界 `rounding_*`、跨 K 块 `tile_*` 三套 `.mem/.bin`，另有各文件哈希清单。

同目录新增机器可读的 [`expected_traces.json`](examples/fp32_hand_image/expected_traces.json)：四个 2×2 输出、非融合舍入例和 `K=32` 边界例都逐项记录 `k`、`x_bits`、`w_bits`、本项累加前位模式、单独舍入后的乘积位模式、累加后位模式，并在所有 `k` 之后记录偏置和最终结果。每个字段都是**候选 FP32 规则**下的 32 位十六进制位模式。`expected_traces.sha256` 保存 JSON 的 SHA-256，便于传给硬件同学后核对文件没有变化；这份记录不是已被 RTL 接受的正式黄金标准。

这只规定**样例文件**的字顺序。它没有分配 E203 可访问的地址，也没有定义 DMA、NICE 命令、矩阵步长或片上缓存的读写仲裁。硬件能否实际按这个顺序接线，需要以后以 RTL 读回表验证。FP32 下 `64×16` 个权重为 4096 字节，放不进一块 2048 字节缓存；此前 16 位原型的“完整 16 列权重驻留”结论不能直接沿用。

## 5. 运行和交给硬件同学的内容

在团队仓库根目录运行（路径中的 `python` 换成当前可用的解释器）：

```text
python -m unittest discover -s software/tests -p test_fp32_reference.py -v
python -m software.examples.fp32_hand_example --output-dir runs/fp32_hand
python -m software.examples.fp32_step_traces --output-dir software/examples/fp32_hand_image --check
```

示例命令会拒绝覆盖非空输出目录。小镜像的 `manifest.json` 记录每个文件的字序列、字节数及 SHA-256。可先让仿真读 `x.mem`、`w.mem`、`bias.mem`，打印每个读到的 FP32 位模式；确认读回与表中值一致后，再比较每个乘积、部分和、最终结果。这一步能把“布局错误”与“算术错误”分开。

`--check` 只重新计算并比较逐步记录及其哈希，不改动已有 `.mem/.bin`。需要在另一空目录重建逐步记录时，运行 `python -m software.examples.fp32_step_traces --output-dir runs/fp32_traces`；生成器只写 JSON 和对应的 SHA-256 文件。若硬件选用不同舍入、FMA、求和顺序或分块保存方式，先共同改定规则，再重建并重新核对这份记录。

跨块样例则读 `tile_x.mem`、`tile_w.mem`、`tile_bias.mem`，检查 `k=31` 后为 `0x40000000`、`k=32` 后为 `0xbf800000`，最后输出 `tile_expected.mem` 中的 `0xbf400000`。若硬件把一块的结束误当成整个点积结束，这个例子会立即暴露问题。

当 RTL 已按同一候选布局写出 `y.bin`，用专门的[`compare_fp32.py`](compare_fp32.py)按 FP32 原始 32 位模式逐元素核对：

```text
python -m software.compare_fp32 --packed-dir runs/fp32_hand \
    --actual runs/rtl/fp32_hand/y.bin --report runs/rtl/fp32_hand/compare.json
python -m software.compare_fp32 --packed-dir runs/fp32_hand \
    --actual runs/rtl/fp32_hand/tile_y.bin --expected-name tile_expected
python -m software.compare_fp32 --packed-dir runs/fp32_hand \
    --actual runs/rtl/fp32_hand/y.mem --report runs/rtl/fp32_hand/compare_mem.json
```

`.mem` 每行必须是一个恰好四位的十六进制 16 位字，依次为每个 FP32 的低字、高字；可有空行，不接受注释或地址标签。工具先检查清单的候选布局、形状、位宽、字数、字节数、`expected.bin` 哈希，再逐个 FP32 比较；报告保存原始 `.mem` 与解码后字节各自的哈希。若硬件采用别的字序，先与硬件同学冻结新协议，再调整打包器和比较器。输出 `BIT-EXACT` 只说明**这份数据、这份候选算术/布局**下各位相同；不是整层、12 层或精度达标证明。旧 `compare_rtl.py` 会把输出解读成整数，不适用于这份 FP32 镜像。

若已有 `x`、`w`、`b` 三个 `float32` 数组组成的 `.npz`，可用 [`pack_fp32.py`](pack_fp32.py) 打包任意尺寸的一层任务。例如：

```text
python -m software.pack_fp32 --input runs/source.npz --output-dir runs/fp32_pack \
    --source-id synthetic/local-check-01 --split synthetic-smoke
```

在 PowerShell 中把续行的 `\` 改成一行输入。工具需要三者的形状分别是 `[M,K]`、`[K,N]`、`[N]`，且它们已明确为 `float32`，不会把 `float64` 悄悄缩窄。若 `.npz` 还包含 `y_float`，它只作来源记录，**不参与生成逐位 `expected`**。`--split` 和 `--source-id` 由提供文件的人声明，脚本记录但无法验证它们确实来自合法比赛数据，也不会用一次打包推断模型精度。以后接真实模型时，要保留合法数据来源、模型版本和输入哈希。

目前尚不能把 `expected.mem` 当作正式 RTL 黄金文件。双方至少还需确认：

1. 每次乘法和加法是否按上面的非融合、逐次 FP32 舍入执行？PE 内部流水是否改变中间精度或加法顺序？
2. 舍入模式是否为 nearest-even？对非规格化数是否逐渐下溢，还是清零？
3. NaN、无穷、溢出及有符号零的规则是什么？本脚本目前主动拒绝 NaN、无穷和溢出；有符号零采用 nearest-even 下的常见规则。
4. K 分块的部分和保存在哪里，保存和恢复会不会多一次格式转换？偏置到底在哪个阶段加？
5. 外存行列顺序、16 位高低字、字节序、真实基地址和总线事务何时定稿？

冻结其中任一项后，同步改脚本、样例与测试，并在清单中记录版本。真正完成联调的证据应是同一版本的 RTL 仿真命令、逐步日志、输出文件和软件比较报告。

## 6. 与硬件独立金标准核对加法和乘法

硬件分支的 `scripts/Generate-Fp32Vectors.ps1` 用 .NET `Single` 生成四列十六进制文件：输入 `a`、输入 `b`、期望加法、期望乘法。硬件同学先在自己的分支生成文件；软件拿到**原文件**后运行 `python -m software.check_hardware_fp32_vectors --vectors runs/fp32_vectors.txt --hardware-commit <生成时的硬件提交> --report runs/fp32_vector_check.json`。比较器逐行严格检查四个 8 位十六进制数，记录文件与软件参考的 SHA-256、通过/跳过/失败数量和第一处位差。`--hardware-commit` 仅记录提供者声明，文件哈希本身不能证明它确实由该提交生成。当前软件草案会明确跳过 NaN/无穷输入及有限数运算溢出为非有限结果的情况，不把跳过计为通过。

2026-10-17 在 `hardware` 提交 `4448aee155f59dc895f83bec3968322160fd66a6` 的生成脚本上，本地生成 20,441 对向量（文件 SHA-256 `b3a645b027dd3a1afddf9ca917f3df35fa4e2aa95222b85ba4c481de168b9dcb`）。有限范围中，加法核对 20,125 对、乘法核对 17,626 对，逐位差异均为 0；加法另跳过特殊输入 314 对、非有限结果 2 对，乘法相应跳过 314 对、2,501 对。**这只交叉核对两套独立参考计算**，并没有运行阵列中的 FP32 PE、偏置、SRAM 或 E203；硬件必须继续提供真实 PE 逐步轨迹和读回日志。
