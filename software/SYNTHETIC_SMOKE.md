# 合成满尺寸向量：先把 RTL 的线路接对

这份工具在**没有官方 KWT-1 权重、没有语音数据、也没有 TensorFlow**时，就能为硬件同学准备完整大小的计算任务。它生成 `X[99,64]`、`W[64,256]`、`b[256]`，并调用当前软件整数模型和打包器得到 `Y[99,256]` 的期望字。

**醒目标记：这些都是人工构造的合成数据，只能用于 RTL/驱动联调。它们不是 KWT-1 的真实激活或权重，不能用来证明 12 层 NRMSE ≤3%，也不能当成比赛精度报告。**

## 一、为什么在等真实模型时还要做它

硬件一旦开始读 SRAM，就容易发生“数算对了，线接错了”的问题。例如 `W[k,j]` 被误当成 `W[j,k]`、最后一行没处理、负数按无符号数读取、偏置只加到第一行、输出低 16 位和高 16 位颠倒。真实模型的几十万个复杂数值很难帮助定位第一处错误。这里先用**能手算的小哨兵值**放进完整大小的矩阵，让硬件像跑正式任务一样处理全部地址，但可以迅速看出错误类型。

它还有一组覆盖所有地址的规律花纹，用于在哨兵通过后检查完整读写。这样做只是功能联调；真实模型和规定样本仍必须另行跑。

## 二、生成与文件结构

在项目根目录，用能运行 NumPy 的 Python 执行：

```powershell
& 'C:\Users\Lenovo\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' software/synthetic_smoke.py --output-dir runs/synthetic_smoke
```

输出目录必须为空。它包含一个总 `manifest.json` 和三个子目录：

| 子目录 | 输入设计 | 最容易抓出的错误 |
|---|---|---|
| `all_zero/` | 所有 X/W/偏置都是 0 | 输出没清零、上一次任务残留、写回不完整 |
| `sentinels/` | 少量人工放置的正负数、偏置、舍入边界与最后索引 | 符号、偏置广播、行列/K 索引、舍入方向 |
| `address_pattern/` | 每个地址都按固定公式生成有符号值 | 中间地址线、步长、权重排布或多块切换 |

每个子目录中：

- `source.npz`：只含合成浮点 `x,w,b`，**没有** `y_float` 键；
- `packed/x.bin`、`w.bin`、`b.bin`：原型格式的输入镜像；
- `packed/expected.bin`：软件数值模型计算的有符号整数输出镜像；
- 同名 `.mem`：一行一个 16 位十六进制字，供 `$readmemh` 等仿真加载；
- `packed/manifest.json`：位宽、小数位、顺序、文件哈希和本地运算信息。

打包清单里的 `reference_kind` 应始终是 `local_numpy_x_matmul_w_plus_b`。这只是对合成数据做本地浮点对照；**其中的 `normalized_rmse` 不是官方 KWT 精度**。

当前原型规定 X/W 为带符号 16 位 Q8，偏置为带符号 48 位 Q16，累加为 48 位 Q16，输出为带符号 32 位 Q8。元素按 C 行优先排列；每个元素的低 16 位字在前，二进制文件中的每个字按小端字节序保存。这个协议还没有得到硬件团队最终确认，后续若协商修改，必须同时更新打包器、软件模型和对拍读法。

## 三、先看几个能手算的输出

`sentinels` 里，`expected` 文件保存的是输出整数 `Y_q`，把它除以 `256` 才是实际数值。例如：

| 输出位置 | 应有的 Q8 整数 | 怎样算出来 |
|---|---:|---|
| `Y[0,0]` | `320` | 该列只有偏置 `1.25`：`1.25×256=320` |
| `Y[98,0]` | `320` | 同一个偏置也要加在最后一行 |
| `Y[0,1]` | `256` | `X[0,0]=1`，`W[0,1]=1`，得到 `1×256` |
| `Y[1,4]` | `-576` | `-2×1.5 + 1×0.5 + 0.25 = -2.25`，再乘 `256` |
| `Y[2,7]` | `1` | 真值只有半个输出最低单位，正向平局按“远离零”舍入 |
| `Y[3,8]` | `-1` | 负向半单位也按“远离零”舍入 |
| `Y[98,255]` | `-1664` | 最后一行、最后一个 K、最后一列：`3×(-2)-0.5=-6.5` |

这组例子刻意区分了 **K 的起始与末尾、输出的首尾列、第一行与最后一行**。若 `Y[0,1]` 正确而 `Y[98,1]` 不对，优先检查 X 行地址或输出行循环。若所有行的第 0 列只在某一行正确，优先检查偏置广播。若只有两个半单位用例错误，优先检查舍入规则。

## 四、与 RTL 对拍的顺序

1. 硬件同学把 `.mem` 或 `.bin` 送进**已约定采用这一原型排布**的 RTL 仿真；保存 99×256 个输出的原始镜像。先跑 `all_zero`，再跑 `sentinels`，最后跑 `address_pattern`。
2. 若 RTL 导出的是与 `expected.bin` 相同的 C 行优先、小端 32 位格式：

   ```powershell
   & 'C:\Users\Lenovo\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' software/compare_rtl.py --packed-dir runs/synthetic_smoke/sentinels/packed --actual runs/rtl/sentinels/y.bin --report runs/rtl/sentinels/compare.json
   ```

   也可以传每行一个 16 位字的 `y.mem`。对拍脚本会报告第一个不同的行、列以及期望/实测的有符号整数与十六进制位型。
3. 保存双方使用的 `manifest.json`、实际输出、对拍报告和仿真命令。看到了 `BIT-EXACT`，只能说明**这组合成向量**与当前软件模型逐位一致；之后还需真实 KWT-1 样本、12 层切换、复位和连续任务测试。

如果硬件最终采用分块排布、不同位宽或 NICE 数据通道，先按双方签字的协议转换镜像或改工具，再比较。直接把另一种排布当作这里的字节序读，会造成误报。

## 五、如何证明向量没有“自己验证自己”

生成器用现有 `create_task_pack()` 算出完整 `expected`。测试另用 Python 标准库 `struct` **直接按字节偏移读取文件**，核对上表的手算整数、最后一项的地址与 48 位负偏置的补码字节；并检查三组数据的完整尺寸、重复生成的输出哈希相同。这些检查不依赖 `pack_tensors.py` 的解包函数复述自身。运行：

```powershell
& 'C:\Users\Lenovo\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' -m unittest software.tests.test_synthetic_smoke -v
```

这仍不等于真实 RTL 验证。正式提交的数值精度必须用指定源码、权重和规定数据划分另行证明。
