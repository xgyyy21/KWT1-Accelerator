# KWT-1 FFN 第一线性层：E203 驱动骨架

这里是一份**可移植的 C 语言流程骨架**，还不是能直接在 E203 SoC 上运行的最终驱动。它没有猜测寄存器地址、NICE 指令编码、DMA 描述符或缓存操作。硬件接口确定后，需要补一个平台适配层，把这些抽象回调接到真实总线和加速器。

本科组必做的一次计算是某个编码层的 `Y[99,256] = X[99,64] × W[64,256] + b[256]`。驱动仅搬运**已经编码、排好顺序的字节**。数值格式和存储布局须由 Python 打包器与 RTL 共同约定；驱动本身不做矩阵乘法，也不在 CPU 上代算赛题要求的计算。

## 一次任务怎样运行

`kwt_run_job()` 依次执行：

1. 检查输入、权重、偏置、输出缓冲区，字节数及层编号 `0..11`。
2. 调用平台提供的 `write`，依次装入输入、权重和偏置。每次回调返回时，整次搬运必须已经完成。
3. 用 `fence` 保证搬运可见；配置矩阵形状及各块字节数；再用 `fence` 保证配置可见。
4. 启动任务，轮询状态；同时使用微秒超时和最大轮询次数，避免无休止等待。
5. 收到 `DONE` 后，执行 `fence` 并读回完整输出。

`FAULT` 或任何回调失败时，不会读取可能尚未写完的输出。返回 `KWT_TIMEOUT` 后应先检查并复位设备，不能直接把同一设备当成空闲再启动。这里的超时从 `start` 返回之后计起；**赛事的任务耗时**应由外层从第一次输入/参数装载开始计到加速器将全部结果写回结束，包含总线等待与 E203 调度。若 CPU 后续逐字读回只为验证，应单列其耗时；不能用 `DONE` 或纯计算周期冒充全部任务时间。计时起止事件须与硬件接口约定并在 SoC 仿真中核实。

## 必须请硬件和数值模型负责人确认的接口契约

- 控制通道用 System Bus 还是 NICE？具体寄存器/命令、完成状态、错误码和中断或轮询规则是什么？
- `X`、`W`、`b`、`Y` 放共享 SRAM、加速器内部 SRAM，还是两者配合？数据由 CPU 搬运还是 DMA 搬运？搬运是否同步完成？
- 每种数据的位宽、符号、字节序、行列顺序、步长、对齐方式是什么？16 位 SRAM 如何容纳 8/16/32 位值？若需要分块，块尺寸和先后顺序是什么？
- `ready/start/busy/done/fault` 如何握手？下一次 `start` 是否清除上一任务的 `DONE`？复位和连续运行 12 层的行为是什么？
- E203、总线或 DMA 是否需要缓存刷新/失效及内存屏障？这些由平台适配层完成。
- `now_us` 使用哪个单调计时源？合理的超时值和轮询等待策略是什么？
- 数据必须在启动前一次装完，还是计算期间按块持续输入？若要持续供块，应先扩展本骨架的回调协议，再用于 SoC 联调。

等上述契约明确后，适配层可实现 `kwt_transport_t` 中的回调。System Bus 和 NICE 都能映射到这个语义层，但具体实现不同。平台适配层必须在 RTL/SoC 仿真中验证。

## 主机端冒烟测试

有 C99 编译器时，在本目录执行：

```sh
gcc -std=c99 -Wall -Wextra -Werror -pedantic kwt_driver.c test_kwt_driver.c -o test_kwt_driver
./test_kwt_driver
```

mock 测试只检查装载、配置、启动、轮询、读回的顺序，以及切换层编号、超时、设备故障和参数错误。测试中的“每元素 1 字节”和固定 `0x5a` 输出只是流程占位值，**不代表量化方案已确定，也不证明数值计算正确**。
