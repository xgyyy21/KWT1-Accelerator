# FP32 首版的分块与搬运草案：先算容量，再谈创新

**状态：可运行的软件推演，尚未经硬件确认。**这份草案服务于当前老师要求的 FP32 首版，计算的是 `Y[99,256]=X[99,64]W[64,256]+b[256]`。它没有证明 150 MHz 时序、真实吞吐、功耗或竞赛得分。已有的 [16 位权重驻留算例](README.md)属于以后可能尝试的量化格式，不能直接拿来描述 FP32 电路。

## 1. 为什么不能简单把 16 位方案照搬过来

FP32 一个数占 4 字节。硬件同学描述的每块 SRAM 容量是 `16 位×1024 字=2048 字节`。完整的 16 列权重是 `64×16×4=4096 字节`，一块放不下。若沿 `k` 方向分两半，每半的权重是 `32×16×4=2048 字节`，恰好占满一块。**这里的 16 位是 SRAM 一个字的宽度；一个 FP32 数要占两个字。**

我们提出一组仅按容量计算的参数：一次算最多 8 行、16 个输出列；64 个输入项分成两个各 32 项的 `K` 块。这样三种暂存需求分别是：

| 暂存内容 | 算式 | 最大容量 |
|---|---:|---:|
| 8 行完整输入 `X` | `8×64×4` | 2048 B |
| 当前 K 块与列块的 `W` | `32×16×4` | 2048 B |
| 8×16 个 FP32 部分和 | `8×16×4` | 512 B |

前两块 SRAM 被数据正好占满；第三块理论上可存部分和。表格没有计地址、状态、可能的双缓冲或端口冲突。**只有硬件同学确认三块 SRAM 能独立承担这些角色、读写端口和时序足够，才算物理上可行。**8×16 与他们计划的 PE 阵列尺寸一致，仍不能由此推断每拍实际产出多少结果。

## 2. 循环顺序决定“搬几次”

候选循环可写成下面的“做事顺序”。`m` 是输入行，`j` 是输出列，`k` 是点积中的位置。`8`、`16`、`32` 是分块大小，最后一块不足时只处理实际元素。

```text
对每个最多 8 行的 m 块：
    把这些行的 64 个 X 全部装入 X 缓冲
    对每个最多 16 列的 j 块：
        把本块的部分和清成 +0
        对 k=0..31、再对 k=32..63：
            把当前 32×16 个 W 装入权重缓冲
            对本块每个输出，按 k 从小到大逐项乘、逐项累加
            第二个 k 块接着第一个块的部分和算，绝不清零
        每个输出只在最后加一次 b[j]，再写出 Y
```

改变不同输出之间的处理顺序，不会改变某一个输出内部的 `k=0..63` 顺序。因此，只要 RTL 也遵守共同确认的非融合、逐步舍入等数值规则，按这个顺序分块在数学上能与我们的 FP32 参考逐位一致。**硬件若使用融合乘加、并行树形归约或不同舍入规则，就必须另写相应参考，不能直接沿用这个结论。**

输入有 99 行，每块最多 8 行，所以要 `ceil(99/8)=13` 个行块，最后一块只有 3 行。输出有 256 列，每块 16 列，所以有 16 个列块。`k` 方向有 2 块。对一个行块，权重整张表仍需读一次；对 13 个行块，整张权重就读 13 次。**不是只读一次**：若想把权重留住直到全部 99 行都用过，同一 16 列的 `99×16×4=6336` 字节部分和无法放进单块 2 KiB SRAM，需要外存回写或另一套存储方案。

## 3. 只隔离比较权重重读

为了公平，把其余逻辑访问在两边设成完全一样：`X` 每元素从共享存储器读一次；`b` 每个输出读一次；`Y` 每个输出写一次。基线则假设每算一行都从共享存储器重读整张 `W`。候选按上面的 8 行分块，每行块重读一次整张 `W`。这只是**逻辑有效载荷字节**，不包括总线协议、对齐、缓存命中、SRAM 内部访问或 DMA 开销。

| 共享存储器有效载荷 | 逐行重读权重基线 | 8 行分块候选 |
|---|---:|---:|
| 读 `X` | `99×64×4=25,344` B | `25,344` B |
| 读 `W` | `99×64×256×4=6,488,064` B | `13×64×256×4=851,968` B |
| 读 `b` | `99×256×4=101,376` B | `101,376` B |
| 写 `Y` | `99×256×4=101,376` B | `101,376` B |
| **总计** | **6,716,160 B** | **1,080,064 B** |

纸面上，权重读取少 `5,636,096` B，总有效载荷少约 `83.92%`。这个数字**不等于**加速 `6.22` 倍，也不等于功耗降低 `83.92%`；真实结果必须在相同频率、模型、数据和硬件资源条件下测量。若基线已有缓存替它复用权重，或三块 SRAM 的端口不足，这个对照就需重新定义。

通用式子（所有元素均 4 字节，行块 `R`）：

```text
共同的 X 读取 = M×K×4
共同的偏置读取 = M×N×4
共同的 Y 写入 = M×N×4
基线 W 读取 = M×K×N×4
候选 W 读取 = ceil(M/R)×K×N×4
仅因 W 重读次数减少而省下 = [M−ceil(M/R)]×K×N×4
```

## 4. 软件已经能检查哪些事

从项目根目录运行：

```powershell
python -m software.innovation.fp32_tiled
python -m unittest software.tests.test_fp32_tiled -v
```

`fp32_tiled.py` 会检查三个暂存区的峰值是否放得下，打印行/K/列块数和上述逻辑字节数。它也提供 `run_tiled_bits`：在小矩阵里模拟分块顺序，保留跨 K 块的部分和，只在最后加一次偏置，与 `fp32_reference.py` 的未分块参考逐位对照。测试含 `k=31/32` 边界、最后不足 8 行/16 列的尾块，以及故意让完整 `64×16` 权重放不进 2 KiB 的失败检查。

**这不是总线流量仪，也没有替硬件排好 DMA 地址。**目前缺少实际 SRAM 端口、缓存用途、地址图、控制接口与 RTL 输出；硬件一旦确认这些，软件才能把这里的候选循环写成正式镜像/驱动调度，并由综合同学测实物级指标。
