# 与硬件同学逐数核对的 2×2 小任务

这是一个**合成的、可手算的线路联调样例**。它沿用当前软件的**原型**格式：`X/W` 是有符号 16 位、8 位小数；偏置和累加器是有符号 48 位、16 位小数；输出是有符号 32 位、8 位小数。乘积按 `k=0,1` 相加，然后加偏置；每次累加都按 48 位范围饱和，最后缩到输出格式时采用“最接近、恰好一半则远离零”。本例数值小，没有触发饱和或半整数舍入。

**这不是 KWT-1 的真实矩阵，也不是比赛精度数据。**双方尚未冻结数值及存储协议；如果硬件最后选了不同格式，应重新生成向量，而不能把本文件当成最终协议。

## 1. 从实数矩阵开始

我们只算两行、两列，点积长度也只有 2：

```text
X = [ 1.0  -2.0 ]       W = [ 2.0  -1.0 ]       b = [ 0.25  -0.5 ]
    [ 0.5   3.0 ]           [ 1.5   0.5 ]
```

`Y[t,j] = X[t,0]×W[0,j] + X[t,1]×W[1,j] + b[j]`。例如第 0 行第 0 列：`1×2 + (-2)×1.5 + 0.25 = -0.75`。四个实数结果为：

```text
Y = [ -0.75  -2.5 ]
    [  5.75   0.5 ]
```

偏置是按**列**加的，所以 `b[0]=0.25` 同时进入 `Y[0,0]`、`Y[1,0]`；`b[1]=-0.5` 同时进入 `Y[0,1]`、`Y[1,1]`。

## 2. 编码成整数，再做乘加

8 位小数表示“实数乘以 `2^8=256`”。因此 `1.5` 存成整数 `384`，`-2` 存成 `-512`。偏置用 16 位小数，因此 `0.25` 存成 `0.25×65536=16384`。每个 `X_q×W_q` 都是 16 位小数的整数，能够直接与偏置整数相加。

| 张量 | 按行排列的编码整数 |
|---|---|
| `X_q` | `[256, -512]`；`[128, 768]` |
| `W_q` | `[512, -256]`；`[384, 128]` |
| `b_q` | `[16384, -32768]` |

逐个输出算，不跳步骤：

| 输出 | `k=0` 乘积 | 加上 `k=1` 乘积后的累加值 | 加上偏置后，Q16 | 转成 Q8 整数 | 解码实数 |
|---|---:|---:|---:|---:|---:|
| `Y[0,0]` | `256×512 = 131072` | `131072 + (-512×384) = -65536` | `-65536+16384 = -49152` | `-49152÷256 = -192` | `-0.75` |
| `Y[0,1]` | `256×(-256) = -65536` | `-65536+(-512×128) = -131072` | `-131072-32768 = -163840` | `-163840÷256 = -640` | `-2.5` |
| `Y[1,0]` | `128×512 = 65536` | `65536+(768×384) = 360448` | `360448+16384 = 376832` | `376832÷256 = 1472` | `5.75` |
| `Y[1,1]` | `128×(-256) = -32768` | `-32768+(768×128) = 65536` | `65536-32768 = 32768` | `32768÷256 = 128` | `0.5` |

第 1 行、第 0 列的 Q16 计算可再核对一次：`768×384=294912`，所以 `65536+294912=360448`。软件原型每次加法都检查 48 位饱和；这里没有溢出，所以普通整数加法与其结果相同。

## 3. 内存中究竟放什么

当前原型把矩阵按行铺平，即 `X[0,0]、X[0,1]、X[1,0]、X[1,1]`，权重按 `W[0,0]、W[0,1]、W[1,0]、W[1,1]`。每个 `.mem` 文本行写一个 **16 位字**；一个 32/48 位元素按**低 16 位字在前**拆开。`.bin` 里每个 16 位字又按**低字节在前**存储。

| 文件 | `.mem` 应逐行出现的十六进制字 | 对应 `.bin` 字节（十六进制） |
|---|---|---|
| `x` | `0100 fe00 0080 0300` | `00 01 00 fe 80 00 00 03` |
| `w` | `0200 ff00 0180 0080` | `00 02 00 ff 80 01 80 00` |
| `b` | `4000 0000 0000 8000 ffff ffff` | `00 40 00 00 00 00 00 80 ff ff ff ff` |
| `expected` | `ff40 ffff fd80 ffff 05c0 0000 0080 0000` | `40 ff ff ff 80 fd ff ff c0 05 00 00 80 00 00 00` |

例如 `Y[0,0]` 的输出整数 `-192` 在 32 位补码中是 `0xffffff40`，拆成低字 `ff40`、高字 `ffff`。`Y[1,0]=1472` 是 `0x000005c0`，所以低字 `05c0`、高字 `0000`。这能直接查出硬件把负数当无符号、把高低字颠倒，或把权重当转置矩阵的问题。

这里的偏置 `-32768` 是 **48 位 Q16 整数**，补码为 `0xffffffff8000`，所以三个 16 位字是 `8000 ffff ffff`。不要把它误当成只有 16 位的偏置。

## 4. 生成文件并交给 RTL 仿真

在项目根目录运行一次；命令拒绝覆盖非空目标目录，以免混入旧版本：

```powershell
& 'C:\Users\Lenovo\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' -m software.examples.hand_2x2 --output-dir runs/hand_2x2
```

会生成 `runs/hand_2x2/source.npz`，以及 `runs/hand_2x2/packed/` 下的 `x/w/b/expected` `.mem` 和 `.bin`、`manifest.json`。脚本把输出文件与上面**独立手算写定的字和字节**逐一比较；若任何一个不同，会报错。先请硬件同学让其小矩阵乘加模块读到这些值，再保存 RTL 输出；如果 RTL 输出采用相同的行优先、小端 32 位排布，可以用：

```powershell
& 'C:\Users\Lenovo\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe' software/compare_rtl.py --packed-dir runs/hand_2x2/packed --actual runs/rtl/hand_2x2/y.bin --report runs/rtl/hand_2x2/compare.json
```

只有这个小例子通过，还不足以证明完整的 `99×64 @ 64×256+b`、12 层换参数、溢出和舍入边界都正确。下一步是 [`SYNTHETIC_SMOKE.md`](../SYNTHETIC_SMOKE.md) 的完整尺寸 `sentinels` 和 `address_pattern`，再接合法语音的真实模型数据。
