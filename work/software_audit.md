# 附录：我们已经写的软件，到底在做什么

> 阅读对象：刚接触芯片设计、矩阵运算和模型量化的同学。这里解释的是工作区 `software/` **现有代码的真实行为**，不是宣称比赛任务已经完成。具体赛题边界仍以[赛题指南](https://mp.weixin.qq.com/s/XQrz5_71pYRwk-U0qIl4SA)为准。

## 1. 先看整条路线

可以把软件工作想象成替硬件准备一道有标准答案的数学题：

```text
真实音频
   ↓ 官方 KWT-1 模型，在电脑上运行
每一层的浮点题目 X、W、b 与标准答案 y_float
   ↓ 选定整数表示法，量化并模拟硬件逐步运算
整数题目 x_q、w_q、b_q 与整数预期答案 expected
   ↓ 按双方约定的次序拆成字节/16 位字
输入、权重、偏置文件  ──→  驱动把数据送进加速器
                              ↓
                         硬件算出整数结果
                              ↓
         ① 与 expected 逐位对比；② 解码后与 y_float 比误差
```

这里的三种“答案”不要混淆：

1. `y_float` 是从指定的原始神经网络中观察到的浮点结果，作为精度参照。
2. `expected` 是我们目前的**暂定整数运算规则**算出的结果，作为未来检查 RTL 的逐位参照。
3. 硬件实际结果现在还不存在，因为目前没有可联调的 RTL 与确定的总线接口。

“浮点”是像 `0.125`、`-1.7` 那样能表示小数的电脑数字格式；“定点”是约定一个缩放倍数后用整数保存小数；“RTL”是硬件同学写的可综合电路描述；“驱动”是 CPU 上负责向硬件装数据、发命令、读结果的程序。

## 2. 题目的线性代数，为什么有四个字母

单个编码层的第一段前馈网络线性计算写成：

\[
Y = XW+b,
\qquad X\in\mathbb R^{99\times64},\quad
W\in\mathbb R^{64\times256},\quad
b\in\mathbb R^{256},\quad
Y\in\mathbb R^{99\times256}.
\]

先不要被形状吓住。`X` 有 99 行，每行 64 个数；`W` 有 64 行、每行 256 个数。矩阵乘法的“中间 64”相同，所以结果有 99 行、256 列。对每一个输出位置 `(t,j)`，做同一件事：

\[
Y[t,j]=\sum_{k=0}^{63} X[t,k]W[k,j]+b[j].
\]

也就是说，把 `X` 第 `t` 行的 64 个数与 `W` 第 `j` 列的 64 个数一一相乘，再把 64 个乘积加起来，最后加上该输出列的偏置 `b[j]`。对 99×256 个输出位置重复。偏置 `b[j]` 沿着 99 行重复使用，叫“广播”。

把数字缩成可以心算的 2×2 小题：

```text
X = [[1, 2],        W = [[5, 6],       b = [9, -1]
     [3, 4]]             [7, 8]]

Y[0,0] = 1×5 + 2×7 + 9    = 28
Y[0,1] = 1×6 + 2×8 − 1    = 21
Y[1,0] = 3×5 + 4×7 + 9    = 52
Y[1,1] = 3×6 + 4×8 − 1    = 49

Y = [[28, 21],
     [52, 49]]
```

实际网络只是把这里的 `2` 换成 `64`，行数换成 `99`，列数换成 `256`。`GELU` 是后续非线性操作；本工程要抽取的是**加完偏置、进入 GELU 之前**的 `Y`。

## 4. 官方参考数据是怎样取出来的

`kwt_reference.py` 的目标，是避免我们凭印象重写完整神经网络。它先核对官方源码与权重文件的固定版本；读取一条长 1 秒、采样率 16 kHz 的音频，即 16,000 个采样值；再尝试让官方 TensorFlow 模型做一次推理。它在 12 个编码层中分别记录：

- `x`：这一层第一段线性计算真正吃进去的 99×64 个值；
- `w`：64×256 个权重；
- `b`：256 个偏置；
- `y_float`：模型第一段 Dense 直接给出的 99×256 个结果。

“权重”是训练得到的乘法系数，“偏置”是乘积和之后加的常数，“Dense”是神经网络框架对 `XW+b` 一类运算的叫法。脚本还安排两项自检：自己用 NumPy 重算 `x @ w + b`，看是否接近 TensorFlow 输出；把抽取过程中重走的网络末尾分类结果与官方网络的分类结果相比。因为浮点加法受计算顺序影响，这里比的是小容差内接近，不是逐位相同。

**状态要说清楚：**目前的机器没有能直接运行该旧版模型的 TensorFlow 环境，工作区里也没有完整的官方权重和合法数据集。因此上述是真实脚本设计及计划执行的检查，**尚没有由它生成且验过的 12 层 `.npz` 文件**。现有测试只检验了 WAV 音频读取和错误模型尺寸会被拒绝。

## 5. 为什么要“量化”：把小数变成整数

电路用整数做乘加通常更省资源。因此先要商量“一个整数代表多大的真实数”。目前示例参数是：

```text
X：16 位有符号整数，小数位 8 位  →  实际值 = X整数 / 2^8
W：16 位有符号整数，小数位 8 位  →  实际值 = W整数 / 2^8
b：48 位有符号整数，小数位 16 位 →  实际值 = b整数 / 2^16
累加器：48 位有符号整数，小数位 16 位
Y：32 位有符号整数，小数位 8 位 →  实际值 = Y整数 / 2^8
```

这里的“位”是二进制位；“有符号”表示能存正数和负数；`2^8=256`。比如实数 `0.5` 用 `X` 格式保存为 `0.5×256=128`。读到整数 `128` 后，再除以 `256` 就还原为 `0.5`。这叫固定小数点位置，也常写作 `Q8`。

为什么 `b` 和累加器都是 16 个小数位？因为 `X整数` 表示“真实值×256”，`W整数` 也表示“真实值×256”，两者相乘后表示“真实乘积×256×256”，即“×65536”。想直接把偏置加到乘积上，偏置也必须先乘 `65536`，单位才相同。这和把 2 米与 30 厘米相加前先统一单位一样。

拿一项乘加完整走一遍：

```text
真实 X = 0.5       → X整数 = 0.5 × 256 = 128
真实 W = 1.25      → W整数 = 1.25 × 256 = 320
整数乘积 = 128 × 320 = 40960
真实乘积 = 40960 / 65536 = 0.625
真实 b = 0.125     → b整数 = 0.125 × 65536 = 8192
累加结果 = 40960 + 8192 = 49152 （仍是“×65536”的单位）
转成输出 Q8：49152 / 256 = 192
输出整数 = 192      → 解码真实值 = 192 / 256 = 0.75
直接用实数核对：0.5 × 1.25 + 0.125 = 0.75
```

真实 `X,W` 常常不能乘 256 后恰好是整数。代码采取“就近取整，刚好卡在两整数中间时远离 0”：例如 `0.1×256=25.6`，存 `26`；`-0.1×256=-25.6`，存 `-26`；若算出正 `25.5`，存 `26`，负 `-25.5`，存 `-26`。输出从 Q16 缩回 Q8 时同样执行这条舍入规则。

位宽有限，所以还有“饱和”：超过该格式最大值时固定为最大值，低于最小值时固定为最小值。16 位有符号整数范围是 `-32768..32767`，所以这里的 X 能表示大约 `-128..127.9961`。超过 `127.9961` 的正实数最终被截在 `32767`。**饱和不是取模回绕**：后者可能把一个很大的正数突然变成负数，二者会算出完全不同的结果。

`ffn1_numeric.py` 的逐元素顺序十分具体：对每一个 `Y[t,j]`，令累加器从 0 开始，依次按 `k=0,1,...,63` 加入 `x_q[t,k]×w_q[k,j]`，**每加一次就对 48 位累加器饱和一次**；全部 64 项做完才加 `b_q[j]`，再饱和；最后从 Q16 缩放到 Q8、舍入并对 32 位输出饱和。这是一个暂定硬件约定，不是所有加速器天然都这样。

为什么“每次加完就饱和”必须写明？用只有 4 位的累加器演示，范围是 `-8..7`。依次加 `7、7、-7`：

```text
先按当前约定：0+7=7；7+7=14→饱和成7；7−7=0。结果是0。
若等全部加完才饱和：0+7+7−7=7。结果是7。
```

即使输入完全一样，运算顺序也会改变答案。RTL 和 Python 必须就这些细节达成**同一份协议**，否则“硬件结果不一致”可能只是双方计算规则不同。

## 6. “打包”是怎样把整数交给硬件的

`pack_tensors.py` 读取一层 `.npz`，调用定点数值模型，分别生成 `x.bin`、`w.bin`、`b.bin` 和 `expected.bin`，以及便于电路仿真的 `.mem` 版本。这里 `expected` 是**软件整数答案**，不是官方浮点答案。

目前采用“行优先、最后一个下标变化最快”的顺序。小矩阵 `W=[[5,6],[7,8]]` 会依次存 `5,6,7,8`，即先 `W[0,0]`，再 `W[0,1]`，接着 `W[1,0]`、`W[1,1]`。正式 64×256 的权重地址若不分块，线性元素序号是 `k×256+j`。输出 `Y[t,j]` 的线性序号是 `t×256+j`。

一个元素可能多于 16 位，于是拆成若干个 16 位“字”，**低有效字先写**。例如 32 位整数 `0x12345678` 拆成 `0x5678` 和 `0x1234`；在 `.mem` 里两行依次为 `5678`、`1234`。在 `.bin` 文件里，每个 16 位字又以小端字节顺序存放，所以实际四个字节依次是十六进制 `78 56 34 12`。32 位的 `-1` 用二进制补码表示为 `0xffffffff`，所以对应两个字都是 `ffff`。48 位偏置每个元素占三个 16 位字。

按这个**示例**格式计算，一层完整数据约占：`X` 有 `99×64=6336` 个 16 位数，即 `12672` 字节；`W` 有 `64×256=16384` 个 16 位数，即 `32768` 字节；`b` 有 256 个 48 位数，即 `1536` 字节；`Y` 有 `99×256=25344` 个 32 位数，即 `101376` 字节。是否有足够 SRAM、是否需要分块、真实的地址先后次序，尚须硬件组共同确定。这些文件目前是**逻辑上的一维镜像**，还不是已经验证过的芯片实际内存地图。

`manifest.json` 是随文件放的一张“说明标签”：记录原始文件和生成文件的 SHA-256 校验值、数组形状、位宽、字节序、储存顺序、运算约定与本地误差。SHA-256 是根据文件内容计算的摘要；两边摘要不同，说明很可能拿错了文件或传输中发生变化。

注意：打包器即使发现 `.npz` 里**没有** `y_float`，也会自行用 NumPy 算 `x @ w + b` 当参考值并生成文件。这样可以测试打包功能，但所得误差**不是与官方模型比较的比赛精度**。即便 `.npz` 含有名为 `y_float` 的数组，打包器本身也无法证明这个数组真的来自官方模型；仍须核对来源清单与提取脚本的运行记录。

## 7. “误差不超过 3%”在当前程序里怎样计算

`evaluate_layers.py` 读取多个样本各自的 `layer_00.npz` 等文件。对某一层，把所有样本中对应输出位置的差值平方、相加，再算均方根：

\[
\operatorname{RMSE}=\sqrt{\frac{\sum_i(\hat y_i-y_i)^2}{N}}.
\]

这里 `y_i` 是该层的官方浮点值，`\hat y_i` 是整数结果重新除以 `2^8` 后的近似值，`N` 是这一层汇总的输出数目。当前程序再除以参考值的均方根作为归一化：

\[
\operatorname{NRMSE}=\frac{\sqrt{\sum_i(\hat y_i-y_i)^2/N}}
{\max\!\left(\sqrt{\sum_i y_i^2/N},\;10^{-8}\right)}.
\]

`10^{-8}` 只是避免分母为 0。拿两个输出做手算：标准值 `[1,2]`，近似值 `[1.1,1.8]`，两个差值是 `[0.1,-0.2]`，平方和为 `0.01+0.04=0.05`；RMSE 是 `sqrt(0.05/2)≈0.1581`；参考均方根是 `sqrt((1²+2²)/2)≈1.5811`；NRMSE 约为 `0.1=10%`。

程序**先在同一层合并所有本地样本的平方和**，再算该层 NRMSE；之后从 12 层中取最大的一个。比如第 0 层 `1%`、第 1 层 `2.5%`、第 2 层 `3.2%`，最大就是 `3.2%`，不能用 12 层平均值把较差的一层掩盖。

这里仍有两个重要限制。其一，程序采用的是**暂定 NRMSE 公式**，正式比赛对“归一化”的定义需对照评测规则核实。其二，本地录音样本即使达到 `3%`，也不能代表未见过的评测数据达到 `3%`。现在 `all_12_layers_present` 要求**每个样本目录**都有完整 12 层；`incomplete_groups` 会列出缺失层。程序还会检查独立 NumPy `X@W+b` 与 `y_float` 是否在容差内，不一致就拒绝报告。但这些检查不能证明音频、权重和 `y_float` 的来源确实是官方模型；正式报告仍须核对提取脚本的来源清单和样本身份。

## 8. C 驱动现在能做什么、不能做什么

`driver/kwt_driver.c` 负责控制一项任务的次序，不负责计算矩阵乘法。`kwt_run_job()` 当前会检查参数，依次调用平台提供的回调写入输入 `X`、权重 `W`、偏置 `b`，随后配置 99/64/256 的任务形状、启动设备、轮询 `DONE` 或 `FAULT`，最后读回输出。`fence` 表示确保前面的写入和配置按要求对设备可见；超时限制可避免设备故障时无限等待。

这里的“回调”可以理解成驱动预留的插口：它只规定“请写入输入数据”“请读设备状态”等动作，暂时没有写这些动作在 E203 的哪条总线、哪个寄存器或哪个 NICE 指令上完成。硬件组还没确定 System Bus / NICE 和寄存器表，所以目前不能直接把这份 C 代码放到芯片上运行。驱动也只检查缓冲区非空、字节数非零、层号在 `0..11`，还不能验证每个文件长度与最终数值协议是否匹配。

当前超时从 `start` 返回后开始计；比赛若统计完整任务时间，外部计时还应包括装载、配置、调度与读回。测试用的 `test_kwt_driver.c` 把设备行为伪造出来，输出全写成 `0x5a`；这个字节只是检查“读回流程有没有执行”的占位符，绝不是神经网络计算结果。

## 9. 到底验证到了哪一步

在 2026 年 10 月 16 日的本地复查中，运行 `python -m unittest discover -s software/tests -p 'test_*.py' -v`，**14 个 Python 单元测试通过**。它们覆盖小矩阵加偏置、量化边界和舍入、累加饱和次序、打包/解包、两条合成样本的逐层误差汇总、缺层报告、不一致参考值拒绝、WAV 数据读取与错误模型形状拒绝。

14 项测试通过的精确含义是“这些预先构造的小例子里，软件函数给出了预计的值”。它**不等于**已经测过比赛的 12 个 Transformer 编码层；测试数量与网络层数也不能混为一谈。

尚缺的运行证据包括：官方权重真实加载；合法音频的官方前向推理；12 个层的真实 `x,w,b,y_float`；在训练/验证样本上的量化选择与本地精度；RTL 与软件逐位对拍；真实 SoC 上由 E203 驱动硬件执行；完整任务耗时、面积、时序和功耗。C 驱动测试在此前环境只做过语法检查，不能写成“C 测试已通过”。

2. **与硬件组冻结数字规则。** 一起明确每种数的位宽和小数位、乘积与累加宽度、偏置何时加入、舍入与溢出处理。用能手算的正数、负数、恰好一半和饱和边界例子达成一致，再更新 JSON、Python 与 RTL。
3. **与硬件组冻结存储规则。** 明确矩阵顺序、16 位字如何拆分、真实 SRAM 容量、地址、分块尺寸与遍历顺序，调整打包器，生成双方共用的同一批文件。
4. **在合法数据上搜数值方案。** 只用允许的样本做标定与调参，逐层看最大误差；核对主办方误差定义，增加参考数据一致性和样本覆盖的严格门槛。
5. **用 RTL 验证整数协议。** 同一份 `x/w/b` 喂给软件数值模型和 RTL，逐字比较 `expected` 与硬件输出；先过小题，再过真实层和边界题。
6. **连接 E203。** 确定 System Bus 或 NICE、寄存器或命令、装载与完成握手，把驱动回调接到真实平台；测量从开始装载到结果读回的完整任务。
7. **留下可复现的证据。** 保存代码版本、环境、输入来源、哈希、运行命令、12 层报告、RTL 对拍记录、SoC 日志与综合报告，让队友能独立重跑。

这就是当前工程的真正位置：**数学与数据格式的参考框架已经写出，并用小例子验证了部分行为；真实模型数据、数值方案定稿和芯片联调仍是后续主体工作。**
