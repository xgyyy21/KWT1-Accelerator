# KWT-1 硬件缓存读回核验：软件侧阶段记录

日期：2026-10-17。核验对象为硬件分支 `acfae7282f2d16f6fe8df476efed147f23df4b71` 中的 `handoff/word_readback.csv`，软件输入是 `software/examples/fp32_hand_image/` 的 9 对 `.bin/.mem` 镜像。本记录只谈 **`matrix_cache_manager` 的 16 位缓存写入与读回**；它不能证明 FP32 乘加、bias、DMA、AI engine、E203 总线或整层任务已跑通。

## 一句话结论

原始 CSV **不能作为已通过来源校验的最终交付**：144 条数据记录的读回字值、32 位重组、地址、坐标和“请求后一拍有效”记录与软件镜像一致，但其中 3 组 `input_sha256` 与实际输入文件不一致。校验器对原始 CSV 返回失败，要求硬件侧重新核实并生成/修正来源指纹，再重新固定 CSV 哈希。

## 核验做了什么

软件侧新增 `software/check_word_readback.py`。它不使用 CSV 中的 `D:/...` 绝对路径去找文件，而是从本仓库手算样例目录打开同名 `.bin/.mem`：

1. 检查镜像清单中的矩阵形状、字数、字节数和 `.bin` SHA-256。
2. 检查 `.mem` 每行恰好一个 16 位十六进制字；按**低 16 位字在前、每字节小端**重建后，必须与 `.bin` 完全相同。
3. 要求 CSV 完整覆盖 3 个算例的 X、W、bias，共 9 组、144 个元素，不能缺行、重复坐标或额外混入其他算例。
4. 每行核对 bank、行列坐标、K 序号、低/高字地址、读回值及重组的 32 位 FP32 位模式。
5. 每行核对低字和高字各自的 `data_valid_cycle = request_cycle + 1`，以及同一张量内部的读回周期顺序。
6. 要求整份 CSV 的 RTL 版本和 RTL 快照指纹一致，并将各组 CSV 声明的输入 SHA-256 与实际 `.bin` 对比。

这些核对是对**现有记录**做的软件审计。软件无法单靠 CSV 证明文件一定是由 RTL 测试台产生，也没有在本次核验中重新运行硬件仿真。

## 发现的 3 组来源指纹错误

下表中的“实际值”由当前软件分支的对应 `.bin` 原始字节重新计算；软件镜像的 `manifest.json` 也记录同一实际值。错误字符串不仅出现在一行，还在该组每个元素的记录中重复。

| 算例/张量 | CSV 中的 `input_sha256` | `.bin` 实际 SHA-256 |
|---|---|---|
| `hand_2x2/W`，`w.bin` | `9b4a9050f1cea2e3bcbb7e5fe240d352eeed38c80b57cd1c9b45a8f9f7c650d7a` | `9b4a9050f1cea2e3bcb7e5fe240d352eeed38c80b57cd1c9b45a8f9f7c650d7a` |
| `rounding_nonfused/W`，`rounding_w.bin` | `c3ab17f29a1c4ba6387856faf4915c03dd5804974feb9ecfddd4fbcc6b41c3ea` | `c3ab17f29a1c4ba6387856faf4915c03dd5804974febb9ecfddd4fbc6b41c3ea` |
| `k32_boundary/BIAS`，`tile_bias.bin` | `75e253f50979177e2ba47b2d0805ad36038789108924514d2a761a70de057d16f` | `75e253f50979177eba47b2d0805ad36038789108924514d2a761a70de057d16f` |

校验器先完成所有行的字值、地址和时序核对，最后汇总这 3 组指纹错误并返回失败。为区分“元数据写错”与“读回数值写错”，我另在**临时诊断副本**中仅替换这 3 组的 `input_sha256`，没有改任何读回字、地址、时序或 RTL 指纹；该副本通过全部 144 条记录的严格核对。临时副本不是硬件交付物，也不应拿它覆盖原始 CSV。请硬件同学从原始输入重新确认这 3 个 SHA-256，并在固定 RTL 快照上重新导出或更正交付文件。

## CSV 自身的三种哈希口径

- 当前 `origin/hardware` Git blob 中的 CSV 使用 LF 换行：SHA-256 为 `6d7de5bfb22f4b817921a47cc79982a23ef8a3d4c45f679d7d8344d76c463250`。
- 硬件进度文档记载的 `61adcaf0e057e060a945e5dca11c11746221950809013805988261674c46272b`，恰好等于把该 Git blob 的 145 个 LF 换行全部换成 CRLF 后的 SHA-256。因此这里能解释为提交时的换行归一化；今后请同时标明哈希针对“本地 CRLF 文件”还是“仓库 LF blob”。
- 用户交来的下一阶段提示词另写了 `d7ba2ee7ae5678552899008b292398df861a6da28d06fa13bfa28dd53e732a1b`。这一值不等于上述两种编码的哈希；当前仓库不能证实它对应哪份文件，请勿当作当前硬件分支 CSV 的哈希使用。

文件本身的哈希必须在最后一次修改后重新计算。不同换行方式即使显示的 144 条内容一样，也会得到不同的文件哈希。

## 如何复查

在 `software` 分支的仓库根目录，使用 Python 以字节方式提取当前 `origin/hardware` 的 CSV，再运行：

```powershell
python -c "import pathlib,subprocess; pathlib.Path('word_readback_from_hardware.csv').write_bytes(subprocess.check_output(['git','show','origin/hardware:handoff/word_readback.csv']))"
python -m software.check_word_readback --csv word_readback_from_hardware.csv --image-dir software/examples/fp32_hand_image
```

截至本记录，这一命令应退出失败并列出 3 组不一致的输入 SHA-256。硬件侧修正、重新提交 CSV 后，重复运行同一命令，目标是 `status: PASS`、`records_checked: 144`、9 组元素全覆盖。若要保存成功时的摘要，可另加 `--report <path>.json`。本地的 `software/tests/test_word_readback.py` 有 7 个小测试，覆盖正常读回、单比特损坏、低高字交换、时序错误、缺失/重复元素和来源哈希错误。

## 给硬件同学的最小行动

2. 核对 `word_readback_tb` 的 `+*_sha=` 输入参数来源，重新生成或修正 CSV。提交固定的 RTL/TB 快照、运行命令、日志和最终 CSV 哈希，注明文件换行方式。
3. `pe_trace.csv` 仍待 FP32 PE 逐步计算测试、bias 贯通和数值约定共同确认后生成；当前缓存读回通过不等于 PE 计算通过。
