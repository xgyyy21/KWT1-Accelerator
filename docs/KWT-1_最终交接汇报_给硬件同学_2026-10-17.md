## 1. 我们共同要完成的首版计算

第一线性层是 `X[99,64] × W[64,256] + b[256] → Y[99,256]`。每个输出 `Y[t,j]` 有 64 项乘积和一次列偏置。首版以 FP32 跑通**可复现的正确性基线**；模型共 12 层，后续需要连续装载、启动、读回。分块和权重复用属于后续可评估的优化，必须保留同输入、同数值合同下的基线。

| 案例及文件前缀 | 软件候选期望，按输出行优先顺序 | 主要检查点 |
|---|---|---|
| 2×2：`x/w/bias/expected` | `bf400000 c0200000 40b80000 3f000000` | 行列索引、负数、每列 bias 广播和只加一次。 |
| 舍入：`rounding_x/rounding_w/rounding_bias/rounding_expected` | **非融合候选** `00000000`；若在关键项融合，可能得到 `a8800000`。 | 区分先把乘积舍入为 FP32 再相加，与 FMA 一次舍入。 |
| K=64 跨块：`tile_x/tile_w/tile_bias/tile_expected` | `k=31` 后部分和 `40000000`；`k=32` 后 `bf800000`；全部算完加一次 bias 得 `bf400000`。 | K32 边界保存和恢复部分和；第二块不清零、不提前加偏置。 |

`expected_traces.json` 按 `cases → 案例 → cells` 记录 `row`、`column` 和 `steps`。每条 `step` 给出 `k`、`x_bits`、`w_bits`、`acc_before_bits`、`product_bits`、`acc_after_bits`；单元末尾有 `acc_before_bias_bits`、`bias_bits`、`result_bits`。这些都是八位十六进制的 **IEEE-754 binary32 位模式**，不需从打印的小数反推。`expected_traces.sha256` 中的 JSON SHA-256 为 `a85bb5b7d334841acab94740290933bd3a991b881acf8782615cb8c43f73553b`，可防止传输后混用不同版本。

生成与核对命令（在解压根目录）：

```text
python -m software.examples.fp32_hand_example --output-dir regenerated
python -m software.examples.fp32_step_traces --output-dir software/examples/fp32_hand_image --check
```

第一条在**空目录**重建 `.mem/.bin`；第二条只检查既有轨迹及其哈希，不改文件。`manifest.json` 是每个镜像文件的逐文件哈希依据。请把这份包及输入文件 SHA 写进 RTL 测试记录，避免同名不同内容。

### 两个仍未冻结的候选约定

1. **算术：**当前软件按有限 binary32、`k=0..K-1`、每次乘法和加法分别以 nearest-even 舍入、**不使用 FMA**、所有乘积结束后偏置加一次生成轨迹。对非规格化数采用逐渐下溢；脚本主动拒绝 NaN、无穷和溢出。这些不是我们单方面给 RTL 规定的正式合同。若 PE 选择融合、不同舍入或不同特殊值策略，请保留 RTL 实测轨迹，双方先定 `numeric_contract_v1.md`，再更新软件期望。
2. **存储：**当前样例暂定每个 FP32 **低 16 位字先、高 16 位字后**；`.mem` 每行一个 16 位十六进制字；`.bin` 的每个 16 位字低字节先。例如 `-0.75f` 的位模式 `bf400000` 对应 `.mem` 的 `0000,bf40` 和 `.bin` 的 `00 00 40 bf`。这只是小镜像协议，**没有**批准外存基地址、片上缓存映射或 E203 字节序。

## 4. 对硬件回复的理解：哪些已有，哪些仍待实现

你们报告已有参数化 `8×16` 脉动阵列、M/N/K 边界 tile 调度、FSM、寄存器边界及 A/B/result 三块各 `16 bit×1024`（各 2 KiB）缓存原型。缓存为同步读，读请求下一拍数据有效，同地址读写读旧值。报告中的回归是 22/22 模块测试、SoC adapter 展开检查和独立 FP32 参考测试 20,441 对。这些都是有用的**模块级/结构级**起点。

你们也明确说明：阵列里的 `pe_mac.sv` 仍为有符号整数 MAC；`fp32_math_pkg.sv` 和 `fp32_mac_boundary.sv` 尚未接进 PE 阵列，目标 FP32 8+4 拍流水、bias、真实 SRAM 数据通路、完整 `99×64 @ 64×256+b` 测试尚未完成；`tile_dma.sv` 目前是地址/握手原型；真实 E203 System Bus/NICE 和外存地址也待定。因此软件不会把 20,441 对**参考模块**测试记为首层 FP32 RTL 通过，也不会据此报时序、面积或能耗。

软件曾提出“8 行 X 放 2 KiB、当前 `K=32×16` 的 W 放 2 KiB、`8×16` 部分和放第三块”的容量推演：分别为 `8×64×4=2048` B、`32×16×4=2048` B、`8×16×4=512` B。**这只证明字节数放得下，不证明现有 A/B/result 三块缓存的端口、调度、读写冲突、bias 路径与部分和恢复已经支持这一映射。**完整 `64×16` FP32 权重需 4096 B，放不进单块 2 KiB。请硬件评估 K32 方案是否可实现；若不采用，请给同样能跨 K 保留部分和的实际方案与测试。

现有 `CTRL 0x00`、`STATUS 0x04`、`SRC_A 0x08`、`SRC_B 0x0c`、`DST 0x10`、`M 0x14`、`K 0x18`、`N 0x1c` 仅是**内部寄存器相对偏移草案**，不是 E203 物理基地址或驱动 ABI。软件不会先把它们写死到平台驱动。
