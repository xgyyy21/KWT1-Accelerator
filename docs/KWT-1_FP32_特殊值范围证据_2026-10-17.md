## 先读结论

目前只能对**一条合成零音频**导出的 12 层 FFN1 数据作检查。它用了指定 KWT-1 权重，但音频并非已确认属于比赛验证集的真实语音。在这批文件里，输入、权重、偏置和保存的浮点输出均未发现 NaN、无穷、次正规数或负零；对这些数组逐 `k` 做的一次数组浮点运算扫描，也没有发现相应的乘积、部分和或末尾偏置加法结果。**这不能保证将来的合法语音、隐藏测试样本和硬件运行永远不会出现特殊值。**

## 2. 这批文件的扫描结果

先按每个 `float32` 数的原始 32 位字段检查：指数全为 1 对应无穷或 NaN；指数全为 0 而小数字段非零对应次正规数；原始位模式 `0x80000000` 为负零。四类张量如下：

| 张量 | 检查元素数 | NaN | 无穷 | 次正规数 | 负零 | 最大绝对值 |
|---|---:|---:|---:|---:|---:|---:|
| 12 层 `x` | 76,032 | 0 | 0 | 0 | 0 | 3.5941663 |
| 12 层 `w` | 196,608 | 0 | 0 | 0 | 0 | 0.4201896 |
| 12 层 `b` | 3,072 | 0 | 0 | 0 | 0 | 0.3005713 |
| 12 层 `y_float` | 304,128 | 0 | 0 | 0 | 0 | 5.4655309 |

还用 NumPy `float32` 数组运算按 `k=0..63` 顺序，逐层依次计算 `product=x[:,k]×w[k,:]`、`acc=acc+product`，最后算一次 `acc+b`，并在每一步检查位字段：

| 扫描对象 | 运算/结果个数 | NaN | 无穷 | 次正规数 | 负零 |
|---|---:|---:|---:|---:|---:|
| 乘法结果 | 19,464,192 | 0 | 0 | 0 | 0 |
| 每步部分和 | 19,464,192 | 0 | 0 | 0 | 0 |
| 末尾偏置加法结果 | 304,128 | 0 | 0 | 0 | 0 |

**边界：**上表的中间值扫描是 NumPy `float32` 数组运算的工程诊断，不是逐个元素调用 `software/fp32_reference.py` 后得到的独立位精确证明；也不能证明 RTL 的实际输出。此处的 0 次发现只适用于上面列出文件哈希的合成数据。

对同一批数据，每层分别取 `A=max|x|`、`B=max|w|`、`C=max|b|`，则这一层任意点积的**精确实数部分和**都有粗上界 `64×A×B`，加偏置后不超过 `64×A×B+C`。12 层中最大的一项约为 **84.9994**（第 0 层），远小于 FP32 最大有限数约 `3.4×10^38`。这些操作按 FP32 舍入产生的微小误差也不可能跨越如此巨大的幅度差，因此这批数据的算术上溢可以排除；但任何新的输入都必须重新给出范围或实测证据。对各层非零输入与非零权重，取两者最小绝对值相乘所得的最小粗下界约 `5.45×10^-12`，远大于最小正规 FP32 正数约 `1.18×10^-38`：这批数据中**非零乘积**不会进入次正规区。部分和可能因为正负抵消而非常小，不能只用这个乘积下界证明部分和永远不次正规；上面的逐步扫描只是对实际这批文件作了观察。

### 最小复核方法

在含有上述 `runs/` 文件的**原项目根目录**运行。Python 需能导入 NumPy；本机曾用 `third_party/venv38/Scripts/python.exe`。下面的代码给出中间运算扫描的核心，代码块可保存到临时 `.py` 文件再运行，输出应为上表三个计数。若文件哈希不同，不能把统计数字视为同一批数据的复现。

```python
from pathlib import Path
import numpy as np

root = Path("runs/reference_smoke/zero_audio_verified")
totals = {name: {"operations": 0, "nan": 0, "inf": 0,
                 "subnormal": 0, "negzero": 0}
          for name in ("product", "partial_sum", "bias_sum")}

def count(name, values):
    bits = values.view(np.uint32)
    exponent = bits & np.uint32(0x7f800000)
    fraction = bits & np.uint32(0x007fffff)
    row = totals[name]
    row["operations"] += values.size
    row["nan"] += np.count_nonzero((exponent == 0x7f800000) & (fraction != 0))
    row["inf"] += np.count_nonzero((exponent == 0x7f800000) & (fraction == 0))
    row["subnormal"] += np.count_nonzero((exponent == 0) & (fraction != 0))
    row["negzero"] += np.count_nonzero(bits == 0x80000000)

for layer in range(12):
    with np.load(root / f"layer_{layer:02d}.npz", allow_pickle=False) as data:
        x, w, b = (data[name] for name in ("x", "w", "b"))
        acc = np.zeros((99, 256), dtype=np.float32)
        for k in range(64):
            product = x[:, k:k+1] * w[k:k+1, :]
            count("product", product)
            acc = acc + product
            count("partial_sum", acc)
        count("bias_sum", acc + b[None, :])

print(totals)
```

## 3. 软件与硬件现在分别做了什么

- `software/fp32_reference.py` 的 `_decode_finite` 遇到输入指数全为 1 就抛出 `UnsupportedFP32Case`，即同时拒绝 NaN 和正负无穷。`_round_dyadic` 遇到运算上溢也抛出同一异常；`software/pack_fp32.py` 会在打包前拒绝非有限的 `x/w/b`。所以“当前软件没算出特殊值”并不等于“软件已支持所有 IEEE 情况”。
- 软件参考对次正规数采用渐进下溢：把极小值按 `2^-149` 为单位舍入，能表示时保留非零次正规数；舍入成零时保留准确符号。对零的加法，`-0 + -0 → -0`，其余零与零相加为 `+0`；乘法零的符号由两个输入的符号异或决定。`software/tests/test_fp32_reference.py` 有对应的边界测试。这些是**已编码并测试的软件草案行为**，还不是硬件正式同意的要求。
- 所查看的团队仓库 `hardware` 分支提交 `4448aee` 中，`rtl/fp32_math_pkg.sv` 的函数实际上已经尝试处理 NaN、无穷、溢出、次正规数和有符号零：例如返回统一的 `0x7fc00000` 安静 NaN、无穷或逐渐下溢后的结果。但这属于**函数级 RTL 实现尝试**，并未使软件合同自动冻结；其异常状态信号、所有边界位模式和完整系统路径仍需共同确认及独立验证。`rtl/fp32_pe_mac.sv` 说明自身是组合函数后加 8 拍乘法、4 拍加法延迟的功能模型，不是已收敛的真正运算流水；当前阵列仍使用整数 `rtl/pe_mac.sv`。
- 硬件分支向量生成器把 NaN 输出位模式统一成 `0x7fc00000`，所以即使将来决定支持 NaN，也需要先约定“全部规范化为统一安静 NaN”还是保留输入 payload；**NaN 的某一个确定位模式不能仅凭十进制 `nan` 推出来**。

## 4. 需要双方商定的两类方案

| 方案 | 具体含义 | 软件要做 | 硬件要做 | 尚缺的证明 |
|---|---|---|---|---|
| A：有限范围合同 | 明确允许输入和每一步中间值的范围；超出时报告错误或另设处理规则。并单独规定是否允许次正规数、有符号零。 | 用真正有来源的训练/验证样本扫描；给出范围、异常计数、12 层误差报告；运行时/输入约束可执行，不能只写“通常不会”。 | 定义超范围检测、错误/状态出口，或依据被证实的输入界实现不可能溢出的算术；接入阵列后对拍。 | 真实数据划分、足够覆盖的样本、模型输入界或可信的运行时检查、接口错误规则。隐藏样本不能靠当前一条零音频保证。 |
| B：完整特殊值语义 | 规定 NaN/无穷、无效运算、上溢、下溢、零符号等所有操作结果；如逐位比对，还要规定 NaN 统一位模式及异常状态。 | 扩展 `fp32_reference.py`、打包/对拍工具与边界向量，分别覆盖输入中特殊值和运算中生成的特殊值。 | 验证/完善 FP32 函数及 PE，把它真正接入阵列，并根据合同提供异常状态或说明无需状态；综合评估面积、时序与功耗。 | 具体 NaN 位模式与状态协议、真实 RTL 回传、综合证据。现有包级函数不能代替整机验证。 |

方案 A 可能节约特殊值处理和验证成本，但**前置约束本身必须可执行且对比赛输入成立**；方案 B 使算术语义完整，但增大硬件验证与实现范围。也可以折中，例如支持有限输入的渐进下溢、对 NaN/无穷/上溢置错误状态；无论选哪一种，必须共同写成可测试的规则。不能把“软件现在会抛异常”直接翻译成“硬件可悄悄给任意结果”。

若选择完整语义，至少要逐项写明：`0×∞` 与 `(+∞)+(-∞)` 等无效运算返回何种安静 NaN；有限运算上溢是否返回带符号无穷；次正规输入与输出是否渐进下溢；`+0/-0` 的结果位；NaN 的 payload/符号是否规范化；是否设置 invalid/overflow/underflow 等状态。IEEE-754 规定了许多数值行为，但**具体对外状态寄存器、软件错误处理、统一 NaN 位模式和系统接口仍是项目合同**。
