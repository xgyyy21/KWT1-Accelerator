# KWT-1：收到硬件 2026-10-17 回复后，软件现在怎么推进

依据[硬件同学的原文回复](KWT-1_回复软件同学_硬件当前状态_2026-10-17.md)，对应硬件提交 `4448aee155f59dc895f83bec3968322160fd66a6`。下文的硬件状态是**对方报告的状态**；软件侧尚未拿到该提交并独立复跑 RTL。本文用于安排下一步，不代替双方签字的数值、存储或控制协议。

## 一、先看清已经有的和还缺的

硬件已报告：8 行×16 列的脉动阵列、分块调度、FSM、寄存器边界以及 A、B、result 三块各 `16 bit × 1024`（2 KiB）的缓存原型；模块测试 22/22 通过，SoC adapter 能展开，单独的 FP32 参考测试通过 20,441 对向量。缓存读请求的有效数据在下一拍出现，同地址读写时读到旧值。这些是模块或结构级证据。

首版任务仍缺关键闭环：阵列中的 `pe_mac.sv` 目前是有符号**整数**乘加；FP32 参考/边界模块尚未接进阵列，FP32 8+4 拍流水和偏置未实现；`tile_dma` 目前只是地址与握手原型；尚无读取完整 `X/W/b` 并写出 `99×256` 个 FP32 结果的测试，也未接入真实 E203、外部 SRAM 和总线。因此现在不能把模块回归写成“FP32 整层通过”或“已有面积功耗成绩”。

三块缓存现名为 **A/B/result**。软件提出把它们用于“8 行 X / 当前 K32×16 W / 部分和”的分块想法，仅通过了容量算术；当前 RTL 的端口、装载、偏置与部分和路径还没有证明这种分工能工作。硬件应决定是否修改映射，或提出另一套可运行调度。

## 二、软件已经备好的三组小任务

文件位于 [`software/examples/fp32_hand_image/`](../software/examples/fp32_hand_image/)；原理、运行命令和限制见[FP32 参考草案](../software/FP32_REFERENCE_DRAFT.md)。每组都有 `.mem`（每行一个 16 位十六进制字）、`.bin` 和哈希清单。**低 16 位字先、每字低字节先**只是候选镜像布局，硬件尚未接受。同目录的 [`expected_traces.json`](../software/examples/fp32_hand_image/expected_traces.json) 还逐输出、逐 `k` 列出输入位模式、乘积、加前和加后部分和、最后偏置和结果；[`expected_traces.sha256`](../software/examples/fp32_hand_image/expected_traces.sha256) 用来校验该 JSON。它们是软件候选轨迹，不表示 RTL 已通过。

| 任务 | 文件前缀 | 必须核对的值 |
|---|---|---|
| `2×2`，含负数与偏置 | `x/w/bias/expected` | 行优先的四个输出位模式：`bf400000, c0200000, 40b80000, 3f000000` |
| 区分逐次舍入和融合乘加 | `rounding_x/rounding_w/rounding_bias/rounding_expected` | 当前**非融合候选**期望 `00000000`；若硬件采用 FMA，需先改数值合同和期望 |
| `K=64`，跨 `k=31/32` 边界 | `tile_x/tile_w/tile_bias/tile_expected` | `k=31` 后 `40000000`，`k=32` 后 `bf800000`，最后只加一次偏置得到 `bf400000` |

镜像生成器是 [`software/examples/fp32_hand_example.py`](../software/examples/fp32_hand_example.py)，逐步轨迹生成器是 [`software/examples/fp32_step_traces.py`](../software/examples/fp32_step_traces.py)，数值实现是 [`software/fp32_reference.py`](../software/fp32_reference.py)。运行 `python -m software.examples.fp32_hand_example --output-dir runs/fp32_hand` 可在空目录重建镜像；运行 `python -m software.examples.fp32_step_traces --output-dir software/examples/fp32_hand_image --check` 可不改文件地核验轨迹及哈希。硬件同学回复中的“请软件提供小向量”，现已具备具体文件；**尚未进入硬件仓库，也未被硬件 testbench 接受**。先交这些文件并记录同一份输入的 SHA-256，不需要重新发明一组不同的小题。

## 三、下一次对接按这个顺序

1. **先读回字，再算数。**硬件用临时 FP32 单 PE testbench 读同一组 `.mem`，打印实际取到的 32 位 `X/W/b`。双方核对高低字顺序；片上 SRAM 的“同步读下一拍有效、同址读写读旧值”也要写进测试时间线。
2. **再对每一步。**对相同输出单元记录原始 32 位输入、每个乘积、每次累加、跨 K 保存/恢复的部分和、最终加偏置及结果。请按 `expected_traces.json` 的输出行列、`k` 和字段逐条对照；若硬件在首个位置不同，保留实际 RTL 日志，不要通过改软件候选答案掩盖差异。由此确定 FMA、舍入、边界值和流水时序；把结论写为 `numeric_contract_v1.md`，再固定正式期望文件。
3. **再定地址。**硬件给 `memory_layout_v1.md`：外存和片上 `X/W/b/Y` 的基址、步长、16 位字序、bias 与部分和位置、K 块装载及写回顺序。软件据此修改打包/解包器，而不把当前草案直接塞进驱动。
4. **再跑整层与 SoC。**先让 `8×16` tile 和 `99×64 @ 64×256+b` 仿真逐位一致，再确定 E203 的 System Bus/NICE、CPU/DMA 搬运、START/DONE/ERROR、最后写回对 CPU 可见的时刻，最后接真实驱动及连续 12 次任务。

当前 `CTRL=0x00`、`STATUS=0x04`、`SRC_A=0x08`、`SRC_B=0x0c`、`DST=0x10`、`M=0x14`、`K=0x18`、`N=0x1c` 是硬件**内部寄存器相对偏移草案**。物理基地址和最终 E203 驱动 ABI 未确定；软件的抽象驱动继续保留，不把这些数字硬编码进去。

## 四、给综合同学的时间点

综合同学现在可以据当前 RTL **准备**工具、工艺库、SRAM 宏库、文件清单、时钟约束和脚本，并做结构检查。首次有意义的加速器综合需要一份版本固定、顶层明确、可综合且能仿真的 RTL。正式任务周期、活动文件、功耗与公平创新对比还要等完整 FP32 任务和 SoC 联调；模块级 22/22 及 20,441 对参考向量都不能代替这些数据。
